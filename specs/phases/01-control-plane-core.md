# Phase 01: Control Plane Core

Goal: build the minimal server that stores platform state and exposes authenticated gRPC API foundations.

## 01.01 Create Server Skeleton

Goal: run a control plane process with gRPC plus local health endpoints.

Inputs:

- Config loader.
- Logging package.

Implementation Notes:

- Add gRPC server listener.
- Add plain HTTP health listener or multiplexed health endpoints for operations:
  - `GET /healthz`
  - `GET /readyz`
- Add gRPC health checking service.
- Add version RPC later in `01.06`.
- Gracefully handle shutdown signals.

Acceptance Criteria:

- Server starts on configured address.
- `/healthz` returns 200.
- `/readyz` returns 200 when persistence is reachable.
- gRPC health check returns serving.
- Shutdown is graceful.

Dependencies:

- `00.04`
- `00.05`

Out Of Scope:

- Authentication.
- App or node APIs.

## 01.04 Add gRPC Authentication Placeholder

Goal: protect operator-facing RPCs with a simple MVP auth mechanism.

Inputs:

- gRPC server skeleton.

Implementation Notes:

- Use token-based auth for MVP.
- Tokens are generated by the server using `crypto/rand` via the shared security helper.
- Tokens are sent on RPC calls as gRPC metadata:
  - `authorization: Bearer <token>`
- Store token lifecycle state in SQLite, not memory.
- Store token hashes, not plaintext tokens.
- Token tables:
  - `admin_tokens`
  - `node_join_tokens`
  - `agent_tokens`
- `admin_tokens` stores:
  - token hash
  - display name
  - created timestamp
  - last-used timestamp
  - revoked timestamp
- `node_join_tokens` stores:
  - token hash
  - intended node name
  - labels
  - created timestamp
  - expiration timestamp
  - used timestamp
- `agent_tokens` stores:
  - token hash
  - node ID
  - created timestamp
  - last-used timestamp
  - revoked timestamp
- Use token prefixes to distinguish token intent:
  - `dep_admin_` for operator/admin CLI access
  - `dep_join_` for one-time node enrollment
  - `dep_agent_` for per-node agent access
- Request validation flow:
  - read `authorization` metadata
  - parse token prefix
  - hash provided token with the server token hashing key
  - query the matching token table
  - reject missing, unknown, expired, used, or revoked tokens
  - attach caller identity to request context
- Caller identities:
  - admin caller for admin tokens
  - node caller with `node_id` for agent tokens
  - join caller only for the node join RPC
- Admin token behavior:
  - generated during `deployer-server bootstrap`
  - displayed once to the operator
  - pasted into `deployer login`
  - used by the CLI for admin/operator RPCs
  - stored by the server as a hash
- Join token behavior:
  - generated by the server when the CLI runs `deployer nodes add <name>`
  - returned once to the CLI
  - displayed as part of the node install/join command
  - one-time use
  - short-lived
  - stored by the server as a hash
- Agent token behavior:
  - generated by the server during successful node join
  - returned directly to the joining agent
  - stored by the agent on the node
  - not normally displayed by the CLI
  - stored by the server as a hash
- Agent tokens map to exactly one node.
- Admin tokens and agent tokens must authorize different RPC sets.
- Require authorization metadata:
  - `authorization: Bearer <token>`
- Exempt health/version RPCs and local health endpoints.
- Keep design replaceable by OIDC-based admin auth later.

Acceptance Criteria:

- Protected RPC rejects missing token.
- Protected RPC rejects invalid token.
- Protected RPC accepts valid token.
- Admin token authorizes admin RPCs.
- Agent token does not authorize admin RPCs.
- Agent token identifies exactly one node.
- Join token cannot authorize normal admin or agent RPCs.
- Tokens survive server restarts because token lifecycle state is database-backed.
- Validation updates `last_used_at` for admin and agent tokens.
- Raw tokens are not logged.

Dependencies:

- `01.01`
- `00.05`
- `00.08`

Out Of Scope:

- Multi-user auth.

## 01.06 Add Protobuf API Contracts

Goal: define shared protobuf request/response contracts used by CLI and agent.

Inputs:

- Planned gRPC services.

Implementation Notes:

- Add `.proto` files under `proto/deployer/v1`.
- Treat `proto/deployer/v1` as the source of truth for control-plane API contracts.
- Generate Go code into `internal/proto/deployer/v1`.
- Use Buf config from Phase `00.01A` for generation and linting.
- Commit generated Go code, but never edit it manually.
- Define initial services:
  - `PlatformService` for version/status.
  - `NodeService` for node join/list/inspect/heartbeat.
  - `AppService` for app deploy/list/inspect/status/logs.
  - `SecretService` for secret management.
- Generate Go code into an internal package.
- Define common list response fields where needed.

Acceptance Criteria:

- CLI, server, and agent can import generated Go protobuf code.
- Proto messages exist for nodes, apps, deployments, routes, and errors/status fields.
- Code generation is included in build tooling.
- `make proto-check` passes after generated code is committed.

Dependencies:

- `00.06`

Out Of Scope:

- REST or OpenAPI spec.
